Overview

What is BANFF?

BANFF (the successor to GEIS) is a generalized system of SAS procedures for the edit and imputation of survey data. It is used primarily at Statistics Canada for handling missing, erroneous, or extreme values in business and household surveys.

Core Design Philosophy

Each BANFF procedure is independent — they can be run in any order or subset. There is no enforced pipeline; the analyst configures the sequence. Data flows through SAS datasets between procedures.

Procedures are stratified by BY variables, which partition records into groups for independent processing (e.g., by industry, region, or size class).

Key Concepts

Edits — linear inequality/equality constraints records must satisfy. BANFF operates in canonical form: all terms on left, constants on right.

Edit groups — sets of variables processed together by a single edit rule set. Records are classified as pass/fail per group.

Field status codes — every field carries a status: original (ok), field to impute (FTI), field to exclude (FTE), or imputed (I*).

Missing data in surveys: Non-response, editing failures, and outlier exclusion all create fields requiring imputation. BANFF provides a structured toolchain to systematically identify which fields need imputing and how to impute them.

Edit Specification — Canonical Form

All edits in BANFF must be expressed as linear inequalities with variables on the left and a constant on the right. The system automatically converts equalities and "≥" forms.

a₁x₁ + a₂x₂ + … + aₙxₙ ≤ b (canonical inequality form)

Example: Revenue − Expenses ≤ 0 (i.e., Expenses ≥ Revenue)
Example: Employees > 0 → −Employees ≤ −1

BANFF also supports edit groups (variable subsets treated together) and data groups (record subsets processed independently via BY variables).

Donor Imputation — Deep Dive

Proc DonorImputation — Theory & Method

Donor imputation is a hot-deck method that replaces missing values in a recipient record by transferring values directly from the most similar valid record (the donor). Because all imputed fields come from one record, the multivariate relationships among variables are automatically preserved — a key advantage over univariate methods.

Step 1 — Record Classification

Before any search begins, every record in the dataset is classified into one of four types relative to each edit group:

TypeInside Edit GroupOutside Edit Group (match fields)Role
Donor All fields pass edits, no FTI flags No FTI flags in user-specified match fields Source of imputed values
Recipient At least one field flagged FTI Any state Receives imputed values
Mixed All fields pass edits (no FTI) At least one FTI in user-specified match fields Cannot donate (ineligible match fields)
FTE Any field marked "field to exclude" — Outlier-flagged: accepted but cannot be donated
FTE (Field to Exclude): These are values flagged by Outlier Detection as extreme enough to be suspicious, but not so extreme as to require changing. The data is kept as-is, but flagged so it is never copied to other records.

Step 2 — Finding Matching Fields

For each recipient, BANFF identifies which of its acceptable fields are informative for predicting the fields to be imputed. This is done via constraint analysis — not heuristically:

  • 1
    Substitute the recipient's known acceptable values into the edit system, reducing it to a system involving only the fields to be imputed.
  • 2
    Identify boundary edits — the subset of reduced edits that actually limit (bound) the feasible region of unknown fields.
  • 3
    Trace back to the original edits. The acceptable fields appearing in those boundary edits are the system-selected matching fields for this recipient.
  • 4
    Append user-specified matching fields (declared outside the edit group) if they have valid values for this recipient.
Why this matters: Two records with the same fields to impute may have different matching fields depending on their acceptable values — because different subsets of the edit constraints will be active (binding) for different records.

Step 3 — Rank Transformation

Raw values of matching fields cannot be used directly in distance calculations because different fields have vastly different scales (e.g., revenue in millions vs. employee count in hundreds). BANFF normalises using rank-value transformation:

Transformed value = rank(x) / (N_valid + 1) where rank(x) is the rank of x among all valid values of that field, and N_valid is the total number of records with a valid value for that field. Tied values receive the average of their ranks.

Properties of the Transformation

Values are mapped to the interval (0, 1), approximately uniformly distributed (except for ties). Extreme values are compressed — the difference between rank 1 and rank 2 is identical to the difference between rank 8 and rank 9, regardless of how far apart the raw values are.

Consequence for Distance

Because all matching fields are now on a common (0,1) scale with equal weight, no single matching field can dominate the distance calculation. The transformation prevents a field with a wide raw range (e.g., revenue) from swamping fields with narrow ranges (e.g., flag variables).

Step 4 — L∞ Distance (Minimax)

BANFF uses the L∞ norm (Chebyshev distance / minimax distance) to measure how similar a recipient is to each donor candidate:

d(recipient, donor) = max{ |x₁−y₁|, |x₂−y₂|, …, |xₙ−yₙ| } where xᵢ and yᵢ are the transformed values of the i-th matching field for the recipient and donor respectively.

This means: the distance equals the largest single-field discrepancy. A donor that is 0.3 off on one field and 0 on all others is considered farther than a donor that is 0.1 off on all three fields — the worst-case mismatch determines closeness.

Step 5 — k-d Tree for Efficient Search

Finding the nearest donor by brute-force comparison against every record would be O(N). BANFF builds a k-dimensional tree (k-d tree) over the donor population to make the search sub-linear:

How the k-d Tree is Constructed
  • 1
    Root node: All donors are placed at the root. The matching field with the largest range of transformed values is selected as the branching field.
  • 2
    Splitting: Donors are split into two halves at the median branching-field value. Equal-sized groups are created; ties are kept together.
  • 3
    Recursion: Each half becomes a child node. The process repeats: choose the largest-range field, split at median, recurse.
  • 4
    Terminal nodes (buckets): Recursion stops when a node holds ≤ 16 donors. These are leaf nodes — the actual donor data lives here.

The tree partitions the k-dimensional matching-field space into non-overlapping regions. Donors in the same region are similar to each other.

How the Tree is Traversed to Find the Nearest Donor
  • 1
    Navigate the tree from root to leaf by comparing the recipient's matching fields against each branching value. This identifies the bucket likely to contain the nearest donor.
  • 2
    Record the n closest donors found so far (user-configurable parameter). Compute the radius = distance to the farthest donor in this set.
  • 3
    Bounds-overlap-ball test: For each unvisited node, check whether a ball of the current radius centered on the recipient overlaps the node's bounding region. If not, the node cannot contain a closer donor — prune it.
  • 4
    Backtrack and visit only unpruned branches. Continue until all branches have been pruned or searched.
Result: Large portions of the donor space are eliminated without checking individual records. This makes the search practical for large datasets.

Step 6 — Donor Selection & Post-Imputation Edits

Once the n nearest donor candidates are assembled, they are tested in order from closest to farthest:

  • 1
    Check that the donor has no FTE flags on fields that would be imputed into the recipient.
  • 2
    Tentatively transfer the donor's FTI-field values into the recipient. Check whether the resulting record passes the post-imputation edits.
  • 3
    If the edited record passes — imputation is accepted. If not — try the next donor.
  • 4
    If all n candidates fail — report failure and move to the next recipient. No imputation performed.

Post-Imputation Edits

Post-imputation edits are typically relaxed versions of the original edits. For example, an equality like A + B = Total is often replaced by a tolerance band: |A + B − Total| ≤ 0.01 × Total. This prevents the search from rejecting all donors simply because no donor happens to produce an exact total match.

Donor Usage Limits

To prevent one record from being used as a donor for too many recipients (which would introduce artificial patterns), BANFF supports a DONORLIMIT:

DONORLIMIT_j = max( NLIMIT, ⌈ MRL × #recipients_j / #donors_j ⌉ )

Once a donor reaches its limit, it is removed from the pool. If no parameter is set, there is no limit.

Recipients with No Matching Fields

When no acceptable field of a recipient appears in the boundary-defining edits, there are no matching fields. The k-d tree cannot be used. Instead, BANFF draws donors at random (if the user enables this option).

Importantly, this rarely causes edit failures: when a recipient has no matching fields, the fields to be imputed are completely unconstrained by the recipient's known values. Therefore, any donor's values can typically be safely transferred — they are already internally consistent.

Estimators — Deep Dive

Proc Estimator — Theory & Algorithms

While donor imputation preserves variable relationships by copying entire records, the Estimator procedure imputes one variable at a time using mathematical models — either estimator functions (direct formulas) or linear regression models. It supports 20 built-in algorithms plus user-defined ones.

Key trade-off: Because each variable is imputed independently, the imputed record may not pass the original edit constraints. Users must re-run ErrorLoc/DonorImputation afterwards to check and correct such failures.

Two Types of Algorithms

Type 1 — Estimator Functions

Direct mathematical expressions involving current and/or historical values of the record being imputed, plus population means. Use four arithmetic operators and exponentiation.

Examples: current mean of all respondents, previous survey value with trend adjustment, ratio to an auxiliary variable.

ŷᵢ꜀ = f(yᵢ꜃, xᵢ꜀, xᵢ꜃, ȳ꜀, ȳ꜃, x̄꜀, x̄꜃, …)

Type 2 — Linear Regression Estimators

Fit a linear model to respondent data, then predict the missing value. Coefficients are estimated by weighted least squares. A random residual can be added to preserve distributional variance.

ŷᵢ꜀ = β̂₀ + β̂₁x¹ᵢᵀ¹ + β̂₂x²ᵢᵀ² + … + β̂ₘxᵐᵢᵀₘ + ε̂ᵢ

Regression Theory — Parameter Estimation

For all regression algorithms, BANFF estimates coefficients using weighted least squares (WLS). This generalises ordinary OLS to handle heteroscedasticity and survey weights.

Model: Y = Xβ + ε Matrix solution: β̂ = (XᵀDX)⁻¹ XᵀDY where: X = design matrix (rows = eligible records, columns = intercept + auxiliary variables) Y = column vector of current values for the variable being imputed D = diagonal weight matrix: D_ii = w_i / v_i^p w_i = record weight (1 if unweighted) v_i = model variance variable (1 if not specified) p = variance exponent
Weighted means used by estimator functions follow the same principle: ȳ꜀ = Σ(wᵢ × yᵢ꜀) / Σwᵢ over all eligible records.

Random Error Term

A key concern with any deterministic imputation method is that it reduces variance in the dataset — all imputed records receive the same predicted value for similar covariate profiles, producing an unrealistically smooth distribution. BANFF addresses this with an optional random error term:

ε̂ᵢ = R_J × √(vᵢᵀ_final / vⱼᵀ_final) where: R_J = residual of randomly selected eligible record J = (y_J − ŷ_J) v = model variance variable (1 if not specified) T_final = final time period in the regression model

The process: (1) compute the predicted value ŷ, (2) randomly select one eligible record J (weighted by survey weights if applicable), (3) compute J's residual, (4) scale by the variance ratio, (5) add to ŷ.

Effect: The random residual reintroduces the natural variability present in the respondent data. The distribution of imputed values more closely resembles the distribution of reported values — important for variance estimation and analysis of the imputed dataset.

Controlling Which Records Contribute to Parameters

BANFF gives the analyst fine-grained control over which records are used to estimate means and regression coefficients:

Exclusion TypeWhat is excludedTypical rationale
FTE exclusion Records with outlier-flagged values in the field to impute or auxiliary variables Outliers would distort means and regression slopes
Previously imputed Records whose relevant fields were imputed in earlier procedures Ensures parameters are based purely on respondent data
User exclusion variable Records where a user-specified condition is true in current or historical file Exclude atypical units, known errors, or out-of-scope records
Automatic exclusion Records missing data in any variable required by the algorithm Ensures numerator and denominator of ratio estimators use identical record sets
Important: Parameters are calculated once before imputation starts and remain fixed throughout the execution. Newly imputed values during a run do not feed back into parameter calculations. Only values imputed in previous executions of Proc Estimator are available.

Algorithm Fallback Chains

Multiple algorithms can be specified for the same variable in one execution. BANFF tries them in sequence: if Algorithm 1 cannot produce a valid value (e.g., auxiliary variable is missing), it tries Algorithm 2, and so on.

Example Fallback Chain

Impute Revenue for non-respondents:

  1. AUXTREND — use prior-year revenue adjusted by employment trend (requires both historical Revenue and current Employment)
  2. PREVALUE — carry forward prior-year revenue (requires historical Revenue only)
  3. CURMEAN — use current group mean (always available)

Records for which Algorithm 1 fails (e.g., first-year respondents with no historical data) automatically fall through to Algorithm 2, and so on.

Imputation Method Comparison

Choosing the right imputation method depends on what structure you want to preserve in the data. Here is a summary of the four BANFF imputation procedures:

Method Unit of Imputation Preserves Relationships Requires Auxiliary Data Theoretical Basis Best Used When
Deterministic Individual fields Exact edit satisfaction No — uses edit structure only Constraint propagation Edit system uniquely determines the missing value
Donor Imputation Full edit group Yes — all fields from same donor Yes — matching fields, auxiliary variables Nearest-neighbour hot deck (L∞, k-d tree) Multivariate relationships matter; sufficient donor pool exists
Estimators One variable at a time Partial — model-based correlations only Yes — auxiliary or historical variables Ratio estimation, OLS/WLS regression Good auxiliary data exists; edit failures after imputation are acceptable
Prorate Component sub-totals Additive consistency enforced No — uses totals only Proportional scaling (raking) Post-imputation cleanup of additive edit failures

Missing Data Theory — Where Each Method Stands

MCAR / MAR considerations

BANFF does not explicitly model the missing data mechanism. However:

  • Donor Imputation is robust under MAR when matching fields capture the reason for missingness
  • Estimators are consistent under MAR when the auxiliary variables explain missingness
  • Neither method handles MNAR without external corrections

Variance Preservation

Single imputation systematically underestimates variance. BANFF's mitigations:

  • Donor Imputation preserves empirical distribution (copies real values)
  • Estimators + random error reintroduce residual variance from respondents
  • Neither is equivalent to multiple imputation for variance estimation
Recommended sequence for complex surveys: Run Deterministic first (catches uniquely-solvable cases), then DonorImputation (handles multivariate records), then Estimator (for remaining individual fields), then Prorate (additive cleanup).
